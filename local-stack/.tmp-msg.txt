Condense an oversized recovery history instead of dropping it

Found while checking whether the new 7-day / 400-message limits were actually
safe: they were not, on any long session.

DEEPSEEK_MAX_HISTORY_CHARS (1.2M here) can exceed DEEPSEEK_MAX_PROMPT_CHARS
(800k). When the replayed history alone pushed the prompt past the cap,
buildBoundedPrompt took its "history is only a hint, drop it first" branch and
threw the entire block away. Measured on a 1500-turn replay: 948,868 chars in,
46 chars out. The session recovered nothing, at exactly the moment recovery
mattered.

Now the history gets a bounded share of the prompt (HISTORY_BUDGET_SHARE, 35%)
and is condensed by lib/context.js, which keeps the opening task, the anchors
(paths, commands, errors) and the newest turns. Same input now yields 279,425
chars with the first turn, the last turn, the live turn and the system prompt
all present.

The old unit test asserted historyDropped === true for this case, which is what
locked the bug in. It still holds for a history with no room left at all; a new
test covers the overflow path and asserts the block survives in condensed form.

Verified live after a full restart with the new limits: a token set before
deepseek-local restart was still recalled afterwards. 107 unit tests pass,
deepseek-local verify reports CHAIN_OK.
